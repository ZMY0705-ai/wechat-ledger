# 01 总体架构

## 1. 需求拆解

| 编号 | 需求 | 承载组件 |
| --- | --- | --- |
| R1 | 微信对话框录入收支 | 微信渠道 + Agent 的 skill |
| R2 | 电脑网页实时更新账目 | 记账服务 + SSE 推送 |

## 2. 三条铁律

这三条决定了整个项目的成败，其余设计都是它们的推论。

### 铁律一：LLM 不做算术

自然语言里的数字交给模型理解（「午饭三十五块」→ 3500 分），**但汇总、占比、余额一律由 SQL 算**。

原因：让模型做「本月食品餐饮 980 / 总支出 3200 = 30.6%」这类运算，短期看着对，长期一定出现
数字漂移——而且用户无法察觉。模型只接收已经算好的结构化数据，负责措辞。

### 铁律二：Agent 不直接改数据库

Agent 通过 `ledger` CLI 写入，而不是直接读写 `ledger.db` 或 JSON 文件。

原因：

| 风险 | 直接写库/文件的后果 | 走 CLI/API 的后果 |
| --- | --- | --- |
| 分类写错 | 静默写入 `吃放`，统计凭空多一个分类 | 校验失败，Agent 收到错误并改用「待分类」 |
| 金额单位混乱 | 一次写 `35`，一次写 `35.00`，一次写 `3500`，账本被污染 | CLI 统一归一为「分」，非法输入直接报错 |
| 重复写入 | 消息重试导致记两笔 | 幂等键拦截，返回既有记录 |
| 并发写坏文件 | 页面读取时拿到半截 JSON | 数据库事务保证一致性 |
| 改错难追溯 | 覆盖式修改，无法回滚 | 软删除 + 审计字段，可撤销 |

**这是本项目最重要的一条：把「理解」和「记账」解耦。**

### 铁律三：所有数字可追溯

每条统计都能下钻到明细，每笔明细都保留 `raw_text`（用户原话）和来源消息 ID。
出问题时能回答「这个 3200 是怎么来的」。

## 4. 三条数据链路

### 链路 A：记账（写入）

```
微信消息
  → 桥接收消息，先判是否确定性指令；否则调 1 次 LLM 做结构化抽取
  → Agent 读 skill 规则，解析出意图
  → exec: ledger add --type expense --amount 35 --category 食品餐饮 --note 午饭 \
            --source wechat --idem <messageId> --json
  → 服务端：校验 → 归一化 → 幂等检查 → 事务写入 → 发布 SSE 事件
  → CLI 返回 JSON（含 id、余额、今日/本月即时汇总）
  → Agent 用返回的数字生成中文回执：「已记：午饭 -¥35.00（食品餐饮）｜今日支出 ¥128.50｜余额 ¥4,231.50」
  → 网页通过 SSE 立刻刷新（无需手动刷新）
```

**两段式确认的触发条件**（避免每笔都问，太烦）：

| 情况 | 行为 |
| --- | --- |
| 金额明确 + 分类明确 + 金额 < 200 元 | 直接记，回执附「如需撤销回『撤销』」 |
| 金额含糊（「几十块」「大概一百多」） | 反问确认 |
| 分类无法判断（「买了点东西」） | 记为「待分类」，回执提示可在网页改 |
| 单笔 ≥ 阈值（默认 200 元） | 草稿确认（`ledger add --draft` → `ledger confirm <id>`） |
| 疑似转账（「银行卡转到支付宝 500」） | 走转账类型，不计入收支 |

### 链路 B：查询与展示

```
浏览器打开 127.0.0.1:8787
  → 首屏：GET /api/summary/dashboard 一次拿齐余额+今日+本月+图表数据
  → 建立 GET /api/stream (SSE) 长连接
  → 任一客户端写入 → 服务端广播 → 所有打开的页面实时刷新
```

### 链路 C：主动汇报与问候

两条路，互为补充：

1. **用户主动打招呼**（「你好」「在吗」）
   → 确定性指令（不过 LLM）→ 调 `ledger brief --json` → 生成日报 + 建议
   → 服务端 `report_log` 记「今天给过了」，同一天再次打招呼只给简版，避免刷屏

2. **开机主动推送**（= 桥接启动时）
   → 拉取 brief 数据，LLM 措辞后投递到微信；电脑休眠唤醒后由看门狗补推
   → 与 1 共用同一套报告逻辑与 `report_log` 去重，输出完全一致

## 5. 组件职责边界

| 组件 | 负责 | 明确不负责 |
| --- | --- | --- |
| bridge（自写桥接） | 渠道接入、意图路由、调 LLM、措辞 | 存账、算账 |
| skill（提示词） | 何时调、怎么解析、怎么回复 | 具体数值 |
| ledger CLI | 参数校验、单位归一、友好报错、幂等键 | 业务规则 |
| 记账服务 | 数据一致性、聚合口径、报表、信号、推送 | 自然语言 |
| 网页 | 展示与人工订正 | 计算（数值全部来自 API） |

边界清晰的收益：**任何一层出问题都能单独替换或单独测试**。换掉微信渠道（比如以后加
Telegram）不用动账本；换掉前端框架不用动 Agent；换掉模型不用动数据。

## 6. 技术选型

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 运行时 | Node.js 22（已装） | 本机已有，零额外安装；桥接零 npm 运行时依赖 |
| 服务框架 | Fastify | 轻、快、内置 schema 校验，好写 JSON Schema 约束 |
| 数据库 | SQLite（`better-sqlite3`） | 单文件、同步 API、事务简单、备份就是复制文件、支持复杂聚合 SQL |
| 前端 | Vite + React + TypeScript | 生态成熟，改动成本低 |
| 图表 | Apache ECharts | 折线/饼图开箱即用，中文文档好，样式可控 |
| 跨端通信 | SSE | 比 WebSocket 简单，单向推送足够；浏览器原生 `EventSource` 带自动重连 |
| CLI | Node + `commander` | 与后端共用同一套 domain 代码，口径不会跑偏 |
| 测试 | Vitest + 内存 SQLite | 聚合口径必须有回归测试，否则改一次错一次 |

**为什么不直接让 Agent 写 Markdown/JSON 账本？** 因为统计需求（月度分类占比、日均线、
跨月对比）在文件上做等于自己写一遍数据库，且没有事务和并发保护。数据量再小，
「查询」这个需求本身就要求结构化存储。

**为什么不直接读微信/支付宝账单？** 可以作为 M4 的补充（导入对账），
但账单滞后、且无法记录现金与非电子支付，不能作为主链路。

## 7. 部署与运行形态

单机三件套，开机自启即可：

| 进程 | 说明 |
| --- | --- |
| `ledger serve` | 记账服务 + 网页 + SSE，监听 `127.0.0.1:8787` |
| `ledger bridge` | 自写桥接（iLink 长轮询 + LLM 抽取 + 内置定时器） |
| 浏览器标签页 | 记账页面，可固定为常驻标签 |

安全边界：

- 服务默认只监听回环地址，不暴露到局域网（如需手机看，加 `--host` 并启用 Token）
- iLink 仅支持私聊，天然不暴露给群；微信侧再加一道：只有本人的号会给 bot 发消息
- 数据库每日自动快照到 `data/backup/ledger-YYYYMMDD.db`，保留 30 天

## 8. 关键决策记录（ADR）

| 决策 | 选择 | 备选 | 理由 |
| --- | --- | --- | --- |
| ADR-1 | 独立记账服务持有数据 | Agent 直接写文件 | 一致性、可测试、口径统一 |
| ADR-2 | Agent 走 CLI 而非裸 HTTP | 直接调 REST | exec 是最稳路径；CLI 可做校验与友好报错 |
| ADR-3 | SSE 而非 WebSocket | WebSocket / 轮询 | 单向推送足够，实现成本最低 |
| ADR-4 | 金额存整数分 | 浮点 / Decimal 字符串 | 杜绝浮点误差，SQL 聚合安全 |
| ADR-5 | 软删除 | 物理删除 | 可撤销、可审计、可对账 |
| ADR-6 | 服务端产出「规则信号」，LLM 只措辞 | LLM 自行分析 | 防幻觉，建议可复现、可解释 |
| ADR-7 | 图表数据由 API 汇总 | 前端拉全量明细自己算 | 明细行数增长后前端会卡；口径统一在服务端 |
| ADR-8 | 接入层自写轻量桥接 + LLM API | OpenClaw / golembot | iLink 协议本身只是几次 HTTP 调用，桥接可控制在 300 行内、零依赖；避免 agent 平台每笔账跑一次完整 agent 轮次的开销，也避免依赖小项目；详见 `docs/04` |
