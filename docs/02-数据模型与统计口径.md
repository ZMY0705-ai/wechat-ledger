# 02 数据模型与统计口径

> 这一章是整个项目的「法规」。口径一旦定下，CLI、服务、前端、Agent 提示词都必须服从；
> 改动口径 = 改动所有统计结果，必须同步更新测试。

## 1. 全局约定

| 项 | 约定 | 理由 |
| --- | --- | --- |
| 金额 | 一律**整数「分」**存储，字段名以 `_cents` 结尾 | 杜绝浮点误差；SQL `SUM` 安全；`3500` 比 `35.00` 无歧义 |
| 金额输入 | CLI 接受 `35`、`35.5`、`35.50`、`￥35`，服务端统一转分 | Agent 与用户都不必记格式 |
| 时间 | `TEXT`，本地时间 `YYYY-MM-DD HH:MM:SS` | 可读、可排序、SQLite 友好 |
| 时区 | 全部按 **Asia/Shanghai**，「今天/昨天/本月」以本地 00:00 为界 | 与用户直觉一致；换算只在服务端做，桥接与 LLM 都不算日期 |
| 日期冗余 | 流水同时存 `occurred_date` / `occurred_month` | 避免每次聚合都做函数计算，可直接走索引 |
| 删除 | 一律**软删除**（`status='voided'`） | 可撤销、可审计；所有统计强制过滤 `status='active'` |
| 方向 | `expense` 支出 / `income` 收入 / `transfer` 转账 / `modify_balance` 余额调整 | 转账与余额调整必须独立，否则「信用卡还款」和「校准余额」会被算成支出 |

**统计通用前提**：所有聚合 SQL 必须带 `status = 'active'`。这是最高频的 bug 来源，
建议在服务层封装 `activeTx` 视图：

```sql
CREATE VIEW active_tx AS SELECT * FROM transactions WHERE status = 'active';
```

## 2. 表结构

```sql
PRAGMA journal_mode = WAL;   -- 允许「页面读」与「Agent 写」并发
PRAGMA foreign_keys = ON;
PRAGMA busy_timeout = 5000;

-- ── 账户 ────────────────────────────────────────────────────────────────
CREATE TABLE accounts (
  id            INTEGER PRIMARY KEY,
  name          TEXT    NOT NULL UNIQUE,   -- 微信钱包 / 支付宝 / 招行储蓄卡 / 现金
  kind          TEXT    NOT NULL DEFAULT 'asset'
                        CHECK (kind IN ('asset','credit','debt')),
  initial_cents INTEGER NOT NULL DEFAULT 0, -- 启用记账时该账户的期初余额
  archived      INTEGER NOT NULL DEFAULT 0,
  sort_order    INTEGER NOT NULL DEFAULT 0,
  created_at    TEXT    NOT NULL
);

-- ── 分类（两级足够：食品餐饮 > 午饭/外卖）──────────────────────────────────
CREATE TABLE categories (
  id         INTEGER PRIMARY KEY,
  name       TEXT    NOT NULL,
  parent_id  INTEGER REFERENCES categories(id),   -- NULL = 一级分类
  direction  TEXT    NOT NULL CHECK (direction IN ('expense','income','both')),
  icon       TEXT,
  sort_order INTEGER NOT NULL DEFAULT 0,
  archived   INTEGER NOT NULL DEFAULT 0
);

-- SQLite 中 NULL 在唯一索引里互不相等，用表达式索引兜住一级分类的重名
CREATE UNIQUE INDEX ux_cat_name
  ON categories(COALESCE(parent_id, 0), name);

-- ── 流水（核心表）──────────────────────────────────────────────────────
CREATE TABLE transactions (
  id             INTEGER PRIMARY KEY,
  occurred_at    TEXT    NOT NULL,   -- '2026-09-10 12:30:00'
  occurred_date  TEXT    NOT NULL,   -- '2026-09-10'
  occurred_month TEXT    NOT NULL,   -- '2026-09'

  type           TEXT    NOT NULL
                 CHECK (type IN ('expense','income','transfer','modify_balance')),
  amount_signed_cents INTEGER NOT NULL CHECK (amount_signed_cents <> 0),

  category_id    INTEGER REFERENCES categories(id),
  account_id     INTEGER REFERENCES accounts(id),   -- transfer 时为「转出账户」
  to_account_id  INTEGER REFERENCES accounts(id),   -- 仅 transfer：转入账户

  note           TEXT,               -- 「午饭」
  raw_text       TEXT,               -- 用户原话：「午饭35」
  tags           TEXT,               -- JSON 数组，如 ["报销"]

  source         TEXT NOT NULL DEFAULT 'web'
                 CHECK (source IN ('wechat','web','import','api')),
  source_msg_id  TEXT,               -- 微信消息 ID
  idem_key       TEXT,               -- 幂等键，见 §5

  refund_of      INTEGER REFERENCES transactions(id),  -- 退款/冲正指向原单

  status         TEXT NOT NULL DEFAULT 'active'
                 CHECK (status IN ('active','voided')),
  voided_at      TEXT,
  void_reason    TEXT,

  created_at     TEXT NOT NULL,
  updated_at     TEXT NOT NULL
);

CREATE UNIQUE INDEX ux_tx_idem  ON transactions(idem_key) WHERE idem_key IS NOT NULL;
CREATE INDEX ix_tx_date  ON transactions(occurred_date,  status);
CREATE INDEX ix_tx_month ON transactions(occurred_month, status);
CREATE INDEX ix_tx_cat   ON transactions(category_id, occurred_month, status);

-- ── 待确认草稿（大额 / 含糊表达）────────────────────────────────────────
CREATE TABLE drafts (
  id            TEXT PRIMARY KEY,    -- 短码 'd7f3a1'，微信里好念好回
  payload       TEXT NOT NULL,       -- JSON：即将写入的参数
  preview       TEXT NOT NULL,       -- 给用户看的中文预览
  source_msg_id TEXT,
  status        TEXT NOT NULL DEFAULT 'pending'
                CHECK (status IN ('pending','confirmed','cancelled','expired')),
  created_at    TEXT NOT NULL,
  expires_at    TEXT NOT NULL        -- 默认 30 分钟，过期不再可确认
);

-- ── 预算（建议功能的输入）──────────────────────────────────────────────
CREATE TABLE budgets (
  id           INTEGER PRIMARY KEY,
  period_month TEXT NOT NULL,        -- '2026-09'；'*' 表示默认值
  category_id  INTEGER REFERENCES categories(id),  -- NULL = 总预算
  amount_cents INTEGER NOT NULL
);
CREATE UNIQUE INDEX ux_budget ON budgets(period_month, COALESCE(category_id, 0));
```

> **实际实现与上面这份 DDL 的差异**（代码在 `server/src/domain/budget.js`，都写在这儿免得对不上）：
>
> - **只写具体月份**（`'2026-09'`），`'*' 默认值` 没有实现。要改下个月的预算就说下个月；
>   隐式的「默认值」会让「这个月为什么是这个数」没法一眼看出来。
> - **只用总预算那一行**（`category_id IS NULL`）。分类预算还没有任何地方能设，
>   API 上就先不暴露这个参数——多一个用不上的口子，只会让「我设了怎么没生效」变得难查。
> - 唯一索引建在**表达式** `COALESCE(category_id, 0)` 上，所以写入用 `UPDATE + INSERT`，
>   不写 `ON CONFLICT`：冲突目标要不要写成表达式，各 SQLite 版本行为不一致。
> - **`amount_cents <= 0` 等于取消**：删掉这一行，而不是留一个 0。0 元和「没设」
>   业务上是两件事，混了会让页面显示「预算 0 元，已花 74.9」。

```sql

-- ── 汇报去重（同一天不重复推晨报）──────────────────────────────────────
CREATE TABLE report_log (
  id          INTEGER PRIMARY KEY,
  kind        TEXT NOT NULL CHECK (kind IN ('morning','greeting')),
  report_date TEXT NOT NULL,
  channel     TEXT NOT NULL DEFAULT 'wechat',
  sent_at     TEXT NOT NULL
);
CREATE UNIQUE INDEX ux_report ON report_log(kind, report_date, channel);

-- ── 元数据（schema 版本、初始余额设置时间等）───────────────────────────
CREATE TABLE meta (key TEXT PRIMARY KEY, value TEXT NOT NULL);
```

### 设计说明

- **为什么冗余 `occurred_date` / `occurred_month`？** 日/月聚合是最高频查询，
  冗余后可直接用索引，避免 `strftime('%Y-%m', occurred_at)` 导致全表扫描。
  写入时由服务端统一计算，不靠调用方传。
- **为什么 `amount_cents > 0`？** 方向由 `type` 表达，金额恒正。
  混用负数会让「支出合计」变成带符号求和，是占比计算的经典坑。
- **`refund_of` 而非负金额。** 退款记为一笔独立 `income`，指向原单。
  这样原始支出仍是真实发生过的历史，退款在当日/当月单独体现。
- **金额字段改名为 `amount_signed_cents` 并允许为负。** 原因是引入了
  `modify_balance`（余额校准）类型：校准可能是调增也可能是调减，单靠 `type`
  承载不了方向。其余三种类型仍要求正数，由服务层校验（见 §4.9）。

```
│                 书籍 / 课程 / 保险 / 税费 / 手续费 / 利息
├── 食品餐饮      早饭 / 午饭 / 晚饭 / 外卖 / 零食饮料 / 买菜 / 请客
├── 购物消费      服饰 / 数码 / 网购
├── 健康医疗      门诊 / 药品 / 体检
├── 出行交通      打车 / 公交地铁 / 加油 / 停车 / 火车机票
├── 休闲娱乐      电影演出 / 游戏 / 旅行 / 运动 / 会员订阅
├── 人情送礼      红包 / 礼物 / 请客随礼
└── 待分类        ← 模型无法判断时的兜底，网页高亮提示人工归位

收入
├── 工资 / 奖金 / 兼职 / 报销 / 投资收益 / 红包收入 / 退款 / 其他收入
```

**唯一的事实来源是 `server/src/db/categories.js` 的 `EXPENSE_TREE`**（上面这份是它的展开）。
清单有两个使用方——新库初始化、老库迁移——所以只有一份定义，改的时候两边一起变。

约定：

- **一级分类是模型和规则解析器唯一会选的东西**。桥接只把一级分类塞进提示词
  （`bridge/src/handler/router.js`），二级分类不参与自动判断，只是网页下拉里的更细标注
  和 `?level=2` 的明细。所以想调整「模型会选哪些」，改的就是这一层。
- Agent **只能**从既有分类中选择，不得自创分类；确实无法判断时落到「待分类」。
  这条直接消灭「吃放」「食品餐饮费」「午饭钱」这类同义分类把饼图切碎的问题。
- 新增分类走网页管理页或 `ledger category add`，人工决定。
  迁移只在 `meta.category_version` 落后时跑一次，不会动你手工加的分类。
- 报表默认按**一级分类**归并；需要看细节时用 `?level=2`。
  这样饼图永远保持在 8~10 个扇区以内。

| 旧一级分类 | 新一级分类 | 做法 |
| --- | --- | --- |

| 交通 | 出行交通 | 原地改名 |

| 通讯 | 生活必需（话费）/ 休闲娱乐（会员订阅） | 旧一级归档，二级分家 |
| 学习 | 生活必需（书籍/课程） | 旧一级归档，二级搬过来 |

两点实现取舍：

- **改名而不是「建新的 + 迁流水」**。id 不变，历史流水的 `category_id` 一动不动，
  迁移就没有「迁到一半失败」这种状态。
- **旧一级分类是归档（`archived = 1`）不是删除**。流水的外键还指着它们，
  删了历史就断了；归档只是从下拉和报表里消失。

## 4. 统计口径（务必逐条固定）

### 4.1 余额

```
总余额 = Σ账户期初余额 + Σincome − Σexpense + Σtransfer转入 − Σtransfer转出
```

单账户：

```sql
SELECT a.initial_cents
     + COALESCE((SELECT SUM(amount_cents) FROM active_tx
                 WHERE account_id = a.id AND type = 'income'), 0)
     - COALESCE((SELECT SUM(amount_cents) FROM active_tx
                 WHERE account_id = a.id AND type = 'expense'), 0)
     + COALESCE((SELECT SUM(amount_cents) FROM active_tx
                 WHERE to_account_id = a.id AND type = 'transfer'), 0)
     - COALESCE((SELECT SUM(amount_cents) FROM active_tx
                 WHERE account_id = a.id AND type = 'transfer'), 0) AS balance_cents
FROM accounts a WHERE a.archived = 0;
```

- `kind='credit'` 的账户余额为负表示欠款，前端显示为「待还 ¥xxx」而非负余额。
- `kind='debt'` 同理表示负债。

### 4.2 日收支

口径：`occurred_date = D AND status = 'active'`，`transfer` 不计入。
输出：收入合计、支出合计、净额、笔数、按分类明细。

### 4.3 月收支

口径：`occurred_month = 'YYYY-MM' AND status = 'active'`，`transfer` 不计入。
月份边界为自然月，本地时区 `[1 日 00:00:00, 次月 1 日 00:00:00)`。

### 4.4 分类占比

```
占比 = 该分类金额 / 同期同方向总额
```

- 分母为 0 时返回 `null`，前端显示 `—`，**不要**返回 0 或 NaN。
- 四舍五入到 1 位小数（`29.9%`），但存储与传输用精确比率，仅展示时舍入。
- 各分类占比之和可能因舍入不等于 100%，属预期行为。

### 4.5 跨月对比必须「同期对齐」

这是一个极易出错的点：

```
本月至今（1 日 ~ 今日）   对比   上月同期（1 日 ~ 上月同一天号）
```

若直接拿「本月至今」比「上月整月」，会得出「本月大幅下降」的错误结论。
上月无对应日号（如 3 月 31 日对上 2 月）时取上月最后一天。

### 4.6 转账

- `type='transfer'` 不计入任何收入/支出统计
- 影响 `account_id` 与 `to_account_id` 两个账户的余额
- 「信用卡还款」「余额宝转入」都是转账，不是支出

### 4.7 退款与冲正

- 退款：新增 `income`，`refund_of` 指向原支出，计入当期收入与当期分类
  （分类沿用原单），报表可用 `?excludeRefund=1` 看「实际消费」
- 记错：`void` 原单（软删除），不计入任何统计，保留审计痕迹

### 4.8 「昨天」的定义

服务端按 `Asia/Shanghai` 计算：`本地今天 − 1 天`，区间 `[00:00:00, 23:59:59]`。
**不接受客户端传「昨天」**，避免时区/时钟不一致导致漏账。

### 4.9 余额调整（modify_balance）

这是一个容易被忽略但迟早会需要的类型：**当账户实际余额与账本算出的一致时，需要一个校准入口。**

典型场景：

- 启用记账时期初余额填错了，后来想修正
- 有几个月没记账，懒得补流水，直接对齐到当前真实余额
- 银行/支付宝账单与手记流水对不上，做一次差异调整

口径规则：

- **不计入任何收入/支出统计**（与 `transfer` 同等对待），不影响分类占比
- 直接改变指定账户的余额，`amount_signed_cents` 可正可负
- `category_id` 必须为空
- `note` 必填，写清调整原因（如「期初余额修正」「9 月漏记对齐」）
- 报表中单独列示，可在明细里看到，但不污染收支

```sql
-- 余额计算中的处理（接 §4.1）
+ COALESCE((SELECT SUM(amount_signed_cents) FROM active_tx
            WHERE account_id = a.id AND type = 'modify_balance'), 0)
```

> 这一条来自对 ezBookkeeping 的对照调研——它的 `TRANSACTION_TYPE_MODIFY_BALANCE`
> 覆盖了同样的场景。我们原设计只有 `initial_cents`，无法在运行中调整余额，
> 属于真实缺口，故补入。

## 4bis. 口径对照：与 ezBookkeeping 的比对

对照对象：`mayswind/ezbookkeeping`（5.6k★，Go，MIT，自托管记账）。
其交易类型定义见 `pkg/models/transaction.go`。

| 我们的设计 | ezBookkeeping | 结论 |
| --- | --- | --- |
| `transfer` 独立类型 | `TRANSACTION_TYPE_TRANSFER` | ✅ 一致 |
| `idem_key` 幂等键 | `ClientSessionId` 字段 | ✅ 一致，验证了幂等设计的必要性 |
| 两级分类（父/子） | two-level categories | ✅ 一致 |
| `account_id` + `to_account_id` | `SourceAccountId` + `DestinationAccountId` | ✅ 一致 |
| `modify_balance` 余额调整 | `TRANSACTION_TYPE_MODIFY_BALANCE` | ➕ **本次补入** |
| 单一 `Asia/Shanghai` 时区 | 每笔存 `UtcOffset` | 我们更简单，个人单时区场景够用 |
| 单一金额 | `SourceAmount` + `DestinationAmount` | 他们为跨币种转账；我们单币种，单金额足够 |
| 软删除 `status='voided'` | 未见对应字段 | 我们更保守（可撤销、可审计），保留 |
| `raw_text` 保留原话 | 无 | 我们保留，用于追溯与调参 |
| `refund_of` 退款关联 | 未见 | 我们保留 |

**另一个重要结论：ezBookkeeping 自带 agent skill（`skills/ezbookkeeping/SKILL.md`）、
CLI 工具（`ebktools.sh` / `ebktools.ps1`）和 MCP 支持。**
它走的是和我们完全相同的架构路线——**用 CLI/MCP 包一层给 agent 调用，而不是让 agent 直接写库**。
这反过来验证了 `docs/01` 里的铁律二是对的。

## 5. 幂等键规则

| 来源 | 幂等键 |
| --- | --- |
| 微信 | `wx:{accountId}:{chatId}:{messageId}` |
| 网页 | 前端生成 `uuid4`，随表单提交 |
| 导入 | `import:{fileHash}:{rowIndex}` |

服务端逻辑：若 `idem_key` 已存在，**不报错**，直接返回既有记录并在响应里标
`"deduplicated": true`。这样 Agent 重试、进程重启、网络抖动都不会重复记账，
且 Agent 无需处理「重复」这个异常分支。

## 7. 规则信号（signals）规格

**建议功能的全部「事实」由服务端产出，LLM 只负责把 signals 翻译成人话。**

| code | 触发条件（阈值可配） | severity | 参数字段 |
| --- | --- | --- | --- |
| `expense_spike` | 昨日支出 > 近 30 天日均 × 1.8 且 > ¥100 | warn | `yesterdayCents`,`avg30Cents`,`ratio` |
| `category_surge` | 某分类本月占比 > 上月同期 + 10pp 且金额 > ¥300 | info | `category`,`shareNow`,`sharePrev` |
| `budget_pace` | 本月支出 / 月预算 > 时间进度 + 15pp | warn | `spentCents`,`budgetCents`,`timeProgress` |
| `budget_break` | 某分类已超月度预算（**暂未实现**：只有总预算，没有分类预算） | alert | `category`,`spentCents`,`budgetCents` |
| `balance_low` | 总余额 < 近 14 天日均支出 × 7 | alert | `balanceCents`,`dailyAvgCents` |
| `no_record_days` | 近 7 天有 ≥ 2 天无任何流水 | info | `days` |
| `top_category` | 本月最大支出分类占比 ≥ 30% | info | `category`,`cents`,`share` |
| `month_over_month` | 本月至今 vs 上月同期偏离 > 25% | info | `nowCents`,`prevCents`,`deltaPct` |
| `zero_spend_streak` | 连续 ≥ 3 天零支出 | good | `days` |
| `regular_due` | 周期性支出（房租/订阅）临近预期日 | info | `label`,`expectedDate` （M4） |

阈值集中在 `server/src/domain/signals.js` 的 `DEFAULT_RULES`（`budgetPaceGapPp` 直接引用
`budget.js` 的 `BUDGET_PACE_GAP_PP`，同一个数字不会两处各写一遍）。

**为什么这么做：** 建议必须可复现、可解释、可测试。LLM 自由发挥的「分析」既不稳定，
也无法回归测试。规则产出信号 + 模板化措辞是唯一能保证「今天说的和昨天逻辑一致」的做法。

## 8. 数据量与性能

个人记账量级：约 10 笔/天 → 10 年 ≈ 3.6 万行。这个量级下：

- 所有聚合 SQL 配好上面的索引后均为毫秒级，无需缓存层
- 折线图取 90~365 天数据仍在毫秒级
- 真正的瓶颈只会是「一次拉全量明细给前端」——所以图表数据必须由 API 汇总返回
