## 2. M-1 连通性验证 ✅ 代码已完成

> **状态：代码已写完并通过单测，接口探测返回 200。**
> 唯一剩下的步骤需要你本人操作：`cd bridge && npm run login` 扫码，
> 把打印出的 `WEIXIN_BOT_TOKEN` 和 `WEIXIN_ALLOWED_USER_IDS` 填进 `bridge/.env`，
> 然后 `npm start` 发一条消息验证。验收清单见 `bridge/README.md`。
>
> 本节以下内容保留原始设计记录，供排障时对照。

自写桥接意味着微信协议这一层要自己实现，所以**先花半天把协议跑通**，
再投入记账内核的开发。

### 第一步：扫码登录，拿到 token

写一个最小的 `bridge/src/weixin/login.js`（✅ 已实现）：

```
① GET  https://ilinkai.weixin.qq.com/ilink/bot/get_bot_qrcode?bot_type=3
   → { qrcode: "<token>", qrcode_img_content: "<二维码URL>" }

② 把 qrcode_img_content 打印出来（先不做终端二维码渲染，直接输出 URL）

③ 每 3 秒轮询，单次 35 秒超时，总超时 5 分钟：
   GET  .../ilink/bot/get_qrcode_status?qrcode=<token>
   → status: wait | scaned | expired | confirmed
   → confirmed 时返回 bot_token、baseurl
```

把这几十行写完，跑一次，确认能拿到 `bot_token`。

### 第二步：验证收消息

写长轮询：

```
POST https://ilinkai.weixin.qq.com/ilink/bot/getupdates
Headers: AuthorizationType: ilink_bot_token
         Authorization: Bearer <bot_token>
         Content-Type: application/json
         X-WECHAT-UIN: <随机数>
Body: { get_updates_buf: "", base_info: { channel_version: "0.1.0" } }
```

用手机给自己发一条消息，确认控制台打印出 `from_user_id`、`client_id`、`context_token`。

### 第三步：验证发消息

```
POST https://ilinkai.weixin.qq.com/ilink/bot/sendmessage
Body: { msg: { from_user_id: "", to_user_id: "<对方>", client_id: "<uuid>",
               message_type: 2, message_state: 2,
               context_token: "<上一步拿到的>",
               item_list: [{ type: 1, text_item: { text: "记账测试" } }] },
        base_info: { channel_version: "0.1.0" } }
```

确认微信里收到「记账测试」。

### ✅ 已完成：接口可达性探测（2026-09-10）

已在开发机实际执行 `bridge/test/probe.js`：

```
HTTP     : 200 OK
耗时     : 284ms
字段     : qrcode, qrcode_img_content, ret
有 qrcode : true
ret      : 0
```

**结论：iLink 接口从本机可达，协议路径成立。** 剩下要验证的是账号能否扫码确认。

### 验收标准

- [x] `node test/probe.js` 返回 200 且有 `qrcode`
- [ ] `npm run login` 能扫码并打印 `bot_token`
- [ ] 长轮询能收到自己发出的消息
- [ ] 能回一条消息到微信
- [ ] 全程零 npm 依赖（只用内置 `fetch`）
- [ ] 确认 401 时是明确报错而非静默失败

### 为什么这一步不能跳过

iLink Bot API **不是微信开放平台的官方接口**，属于腾讯的另一套服务。虽然 golembot 的
实现证明它可用（我们已经核对了源码，协议细节见 `docs/04` §2），但：

- 它可能随时变更
- 你的账号不一定在灰度范围内
- 网络环境可能不通

**花半天排除这个不确定性，比写完一整套记账系统再发现通道不通划算得多。**

如果 M-1 失败，备选依次为：

1. **企业微信（WeCom）官方 API** —— 合规、稳定，但需要企业微信账号，
   且要自己接一层应用消息推送
2. **OpenClaw 官方微信插件** —— 同一套 iLink 协议，但由腾讯微信团队维护，
   若我们直连不通，可以借用它的通道
3. **降低目标** —— 先用网页手记，微信通道延后

### M2 桥接开发 ✅ 已完成（2026-09-10）

> **落地情况**：`llm/prompt.js`、`llm/client.js`、`handler/{router,commands,record,compose,drafts}.js`
> 全部实现并有过测试覆盖（`bridge/test/llm.test.js`、`bridge/test/handler.test.js`）。
>
> 与原始设计的两处偏差，都是刻意的：
>
> 1. **草稿存在桥接侧**（`data/bridge-drafts.json`），没有走 `docs/03` §2 里的
>    `/api/drafts`。理由：草稿是「一段对话的临时状态」，不是账本事实；
>    单机单用户场景下放桥接更简单，且桥接重启也不丢（落盘）。
>    代价是网页上看不到未决草稿——如果以后想让网页也参与确认，再把它挪到服务端。
> 2. **LLM 不可用时降级到服务端规则解析**，而不是直接报错。
>    原始设计里只有确定性指令不过模型；实测下来，`server/src/domain/parse.js`
>    已经能覆盖 `docs/07` §3 的全部 12 条语料，白白不用太可惜。
>    降级是显式的——回执会注明「本轮没有用上模型」，不冒充模型的判断。
>
> 为了让服务端成为唯一口径，新增了 `POST /api/parse`（干跑，只算不写）：
> 桥接把模型结果连同原话一起发过去，由服务端做分类强校验、相对时间换算、
> 置信度评分与硬规则判定。桥接自己不算日期、不算金额、不校验分类。

范围（在 M-1 已跑通的骨架上补齐）：

### M3 晨报与建议 ✅ 已完成（2026-09-10）

范围（实际落地的版本与计划的两处差异见下）：

- 服务端 `GET /api/report/brief`：9 条规则的 `signals` 引擎、`report_log` 去重、`fallbackText`
- 桥接 `handler/brief.js`：拼装日报 → 措辞 → 主动发送 → **发送成功之后**才 `markSent`
- 触发方式：**桥接启动时推当天那一份**（= 你开机），不是 08:30 定时 cron
- 打招呼触发的即时汇报（当天第一次给完整日报，之后只报数字）
- `node src/index.js --brief`：只打印不发、不标记，用来预览「今晚会收到什么」

验收标准：

- [x] 开机（= 桥接启动）后微信收到日报：昨日 / 本月 / 余额 / 建议
- [x] 发「你好」也能收到同样结构的日报
- [x] 同一天再次打招呼只给简版，不重复轰炸
- [x] **桥接重启后日报仍能发出**（`context_token` 持久化生效）
- [x] 若发送失败 → `report_log` 无记录 → 下次启动自动补发（重启后 `alreadySentToday` 仍为 false）
- [x] 建议内容全部可追溯到 `signals`，无编造数据
- [x] 每条 `signals` 都有对应文案（`SIGNAL_CODES` 守卫测试；`budget_absent` 就是这么被揪出来的）
- [ ] 🔌 真机验证：关机一晚，第二天登录后确认微信收到日报（要你本人跑）

**差异一：定时晨报 → 开机推送。** 这台电脑不是 24 小时开着的。定时任务在关机期间
只会白白错过，而且错过之后没有任何补救机会；挂在桥接启动上，则保证「开机后一定会
看到今天的账」。`report_log` 保证一天只推一次，反复重启也不会重复打扰。
另外启动阶段发送失败会重试（最多 6 次 × 1 分钟）——开机那一刻推不出去，当天就没了。

**差异二：日报里带不了截图。** iLink Bot API 的官方实现只发文本
（发送报文是 `item_list: [{type:1, text_item:{text}}]`，CDN 那条路径只用于**下载**图片，
没有对外的图片上传/发送接口）。所以日报是纯文字的：数字一个不少，图要看就开
<http://127.0.0.1:8787>。

### M4-1 月度预算 ✅ 已完成（2026-09-10）

范围**只做「本月总预算」**：`budgets.category_id` 留空不用。分类预算得先有地方能设，
否则多暴露一个参数，只会制造「我设了怎么没生效」这种查不出原因的疑问。

| 层 | 落点 |
| --- | --- |
| 领域 | `server/src/domain/budget.js`——`getBudget` / `setBudget`（0 = 取消）/ `computeBudgetStatus`（纯函数，便于穷举边界） |
| API | `GET /api/budgets?month=`、`PUT /api/budgets`；成功广播 `budget.updated`；dashboard 里带一份，首屏少一次往返 |
| CLI | `ledger budget show / set / clear`；人类可读输出是「支出 vs 时间」双进度条 |
| 网页 | 余额卡下方的「本月预算」卡片，点「改预算」就地变输入框，SSE 自动刷新 |
| 建议 | `budget_pace` 信号复用同一个阈值；没设预算时 `budget_absent` 引导去网页设置 |

三个刻意不做的决定：

- **不给「按当前速度月底会花到多少」的线性外推。** 交一次房租就能把它顶到月支出的两倍，
  看着像真数字，其实是在把一次性支出摊到整月。宁可少说一句。
- **节奏比的是比例，不是金额。** 花了 20% 而时间过了 33% 是省着花，反过来才叫「快」。
  金额大小只说明预算总量，比例才是可比的。
- **阈值只写一次。** `signals` 的 `budgetPaceGapPp` 直接引用 `budget.js` 的
  `BUDGET_PACE_GAP_PP`——同一个数字写两遍，迟早会对不上。

> **实现语言说明（已落地的实际选择）**：整个仓库都是**纯 JavaScript + 零 npm 依赖**，
> 包括原本计划用 TypeScript 的 `server/`、`cli/`、`web/`。

> 而是原生 ES module + 手写 SVG 图表。
>
> 上面这份目录树保留的是**原始规划**，实际结构以仓库为准；
> 差异较大的地方（`server/src/api/` 尚未拆分、`signals.ts` 还没写）会在对应里程碑里对齐。

## 5. 风险清单

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| **iLink Bot API 非微信开放平台官方接口** | 协议可能变更，通道随时可能失效 | **M-1 先验证**；桥接独立隔离在 `bridge/`，出问题只换接入层不动账本；备选企业微信官方 API |
| **`bot_token` 会过期（401）** | 突然收不到消息 | 明确告警不静默失败；重跑 `npm run login` |
| **`context_token` 可能过期** | 主动发送失败（晨报漏发） | 落盘持久化 + 打招呼兜底补发（共用 `report_log`，见 `docs/04` §7） |
| LLM 抽取错误（分类错、金额错） | 账目不准且不易察觉 | 分类/类型用提示词清单 + 服务端强校验双重约束（两家 LLM 都不支持 json_schema）；model 与服务的置信度取低值；大额/金额缺失/转账走硬规则确认；回执必带金额与分类；撤销入口 |
| LLM 服务不可用 | 无法记账 | 确定性指令（撤销/余额/报表）不依赖 LLM；回执有 `fallbackText` 兜底 |
| 微信消息 2000 字符上限 | 长回复排版乱 | 回执压到 8 行内，超长主动切分 |
| 桥接进程崩溃 | 收不到消息 | 开机自启 + 进程守护；长轮询自带指数退避重连 |
| 记账服务未启动 | 桥接报错、晨报失败 | 开机自启；桥接检测到服务不可达时明确提示 |
| 认证信息泄露 | `bot_token` 等同微信收发信权限 | 只放 `.env` 并加入 `.gitignore`；不写入日志 |
| 分类体系膨胀 | 饼图碎片化，占比失去意义 | 分类只增不改由人工控制；enum 从数据库生成；报表按一级归并 |
| 跨零点 / 时区不一致 | 「昨天」算错一天 | 服务端固定 `Asia/Shanghai`；时间换算只在服务端做 |
| 数据丢失 | 不可接受 | WAL + 每日 `VACUUM INTO` 快照（保留 30 份）+ CSV 全量导出 |
