## 1. 可直接借鉴的部分

### 1.1 分类体系与关键词

auto-bookkeeping 的 12 分类及触发词：

| 分类 | 关键词示例 |
| --- | --- |
| 餐饮 | 饭、餐、奶茶、咖啡、外卖 |
| 交通 | 打车、滴滴、公交、地铁、油费 |
| 购物 | 买、超市、淘宝、京东 |
| 娱乐 | 电影、游戏、KTV、健身 |
| 住房 | 房租、水费、电费、物业 |
| 医疗 | 医院、药、体检 |
| 教育 | 学费、培训、书 |
| 通讯 | 话费、流量 |
| 工资 | 工资、薪资、奖金 |
| 副业 | 兼职、稿费、佣金 |
| 理财 | 利息、分红、基金 |
| 其他 | 未匹配时默认 |

对照我们 `docs/02` §3 的分类体系，有两点差异值得吸收：

- **它的分类里混了收入和支出**（工资/副业/理财是收入）。我们的设计是**按方向分开**的，
  这点我们更好，保持。但可以借鉴它的关键词表来填充我们 `categories` 表的匹配词。
- **「其他」是默认兜底**。我们用「待分类」，语义更好——「其他」会被误认为一个正常分类，
  「待分类」自带待办含义，能驱动用户去归位。保持我们的做法。

### 1.2 支持的输入格式

**时间词**（原文列出）：

```
今天 / 昨天 / 前天 / 周X / 上周X / N天前 / M月D日 / YYYY-MM-DD
```

**金额格式**（原文列出）：

```
30 / 30元 / 30块 / 30.5 / ¥30
```

这两个清单可以直接作为我们 `ledger parse` 的用例集。

### 1.3 置信度阈值机制

原文规则：

```
confidence >= 0.6：直接记录，无需确认
confidence < 0.6 或 amount 为 null：展示解析结果，询问是否正确
```

**0.6 这个阈值是可直接采用的**。它的示例中，「昨天午饭兰州拉面30元」这样要素齐全的句子
得到 0.67——说明这个阈值定得比较宽松，偏向「少打扰用户」。这符合记账场景的体验要求。

### 1.4 低置信度确认模板

```
📝 准备记录：
  日期：2026-06-13
  金额：¥30.00
  分类：食品餐饮
  备注：午饭兰州拉面
  类型：支出

确认记录吗？（直接回复"是"或修改后确认）
```

这个模板已经很好，直接采用。

## 2. 我们自己的置信度评分设计

原 skill 没公布权重，只给了阈值。下面是我们补的评分细则——**维度加权求和**，
满分 1.0，阈值沿用 0.6。

| 维度 | 权重 | 判定与得分 |
| --- | --- | --- |
| **金额** | 0.45 | 显式数字（`35` / `35元` / `¥35`）= 1.0<br>含模糊词（`几十块` / `大概一百多`）= 0.2<br>完全缺失 = 0（触发强制追问） |
| **类型** | 0.25 | 明确动词（花/买/付/交 ↔ 收/发/赚/报销）= 1.0<br>可由分类推断（如「房租」必为支出）= 0.6<br>无法判断 = 0 |
| **分类** | 0.20 | 精确命中关键词表 = 1.0<br>模糊匹配到候选 = 0.5（落「待分类」）<br>无匹配 = 0.2（落「待分类」） |
| **时间** | 0.10 | 显式表达（`昨天` / `6月5日`）= 1.0<br>未提及（默认今天）= 0.5 |

`confidence = Σ 权重 × 得分`

**示例核算**——「昨天午饭兰州拉面30元」：

```
金额 0.45×1.0 = 0.45   （30元，明确）
类型 0.25×1.0 = 0.25   （语义上是消费）
分类 0.20×1.0 = 0.20   （午饭 → 食品餐饮，精确命中）
时间 0.10×1.0 = 0.10   （昨天，显式）
              = 1.00  → 直接记账
```

原 skill 给出的是 0.67，我们算出 1.00。差异在于我们用了加权求和而它可能用了更保守的
逐项扣分。**这不重要**——重要的是阈值行为一致：要素齐全就静默记账。

**示例核算**——「买了点东西」：

```
金额 0.45×0.0 = 0.00   （缺失 → 强制追问，分数不参与决策）
类型 0.25×1.0 = 0.25   （买 → 支出）
分类 0.20×0.2 = 0.04   （无匹配 → 待分类）
时间 0.10×0.5 = 0.05   （未提及）
              = 0.34  → 必须确认
```

### 2.1 硬规则优先于分数

无论分数多高，以下情况**必须**向用户确认。这是防止「高置信度地记错账」的关键：

| 硬规则 | 动作 |
| --- | --- |
| 金额缺失或 ≤ 0 | 追问具体金额 |
| 单笔 ≥ 200 元（可配置） | 展示解析结果，等确认 |
| 识别为转账 | 必须问清转出/转入账户 |
| 时间落在未来 | 追问确认 |
| 分类落入「待分类」且金额 ≥ 100 元 | 提示分类，可在网页改 |

**为什么硬规则要压倒分数**：权重和阈值是启发式的，会有把错的判成对的的时候。
但「金额缺失」「大额」「转账」这三类错误代价最高且最容易识别，用确定性规则兜住它们，
比调权重可靠得多。

## 4. 与现成方案的取舍

| 维度 | auto-bookkeeping | 我们 |
| --- | --- | --- |
| 存储 | SQLite（脚本未提供） | SQLite（自己实现） |
| 分类方向 | 收入支出混在一起 | **按方向分开** |
| 兜底分类 | 「其他」 | **「待分类」**（语义更强，驱动归位） |
| 报告 | 生成静态 HTML 文件 | **实时网页 + SSE 推送** |
| 主动汇报 | 无 | **每日晨报 + 打招呼补发** |
| 建议 | 无 | **signals 规则 → LLM 措辞** |
| 幂等 | 未见 | **idem_key** |
| 金额精度 | `float`（JSON 里是 `30.0`） | **整数分**，避免浮点误差 |

最后一行值得强调：原 skill 的解析结果用浮点数（`"amount": 30.0`），
而我们坚持整数分（`amount_cents: 3000`）。**在记账系统里这是必须的**，
浮点数做多次求和会累积误差，而余额是要和真实银行账户对得上的。
