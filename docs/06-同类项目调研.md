## 1. 结论先行

1. **有大量同类项目，但没有一个完全对上你的需求。** 现成方案都停在
   「自然语言记账 + 本地存储 + 生成报告」，**没有**「实时网页（SSE 推送）+ 每日主动汇报 + 花费建议」。
2. **不用从零写。** 解析规则、分类体系、报告模板都能直接借鉴，甚至整块复用。
3. **最大的意外收获是 `golembot`** —— 它让「Codex + 微信」这个组合真的成立，
   直接回答了上一轮的疑问。
4. **最大的风险发现**：基于「网页版微信协议」的方案正在失效（作者自述约两天掉线一次），
   iLink API 是当前唯一可靠的个人微信路径。

## 2. 直接回答「Codex 能接微信吗」

### `0xranx/golembot` — 322★ · MIT · Node ≥18

> "One command connects your Coding Agent to Slack, Telegram, Discord, Feishu, DingTalk,
> **WeCom, WeChat**, or any HTTP client — with any LLM provider."
> —— 官方 README

- 支持的「大脑」：**Claude Code、Codex、OpenCode、Cursor**
- 支持的渠道：Slack / Telegram / Discord / 飞书 / 钉钉 / **企业微信 / 微信** / HTTP API
- 一句话启动：`golembot init -e claude-code -n my-bot` 然后 `golembot gateway`
- 兼容 ClawHub 上 **13,000+ OpenClaw 社区 skill**
- 设计理念与我们的判断一致：「不写 AI 框架、不做 prompt 工程，你已有的 agent **就是**大脑」

**最终定位**：我们**不把 golembot 当平台用**，而是把它的微信协议实现当作**参考实现**——
它证明了 iLink Bot API 可用且极简（纯 HTTP，零 SDK），我们据此自己写桥接（MIT 许可）。
协议规格已完整提取到 `docs/04` §2。

**已核实的事实**：

- 微信通道走的是 **腾讯 iLink Bot API**（`ilinkai.weixin.qq.com`），与 OpenClaw 官方插件
  **同一套协议**——不是正在失效的网页版微信协议
- **零 npm 依赖**，只用内置 `fetch` 做 HTTP 长轮询
- 仅支持私聊；有 `tasks` 定时任务能力；`skills/` 目录 + `AGENTS.md` 与 OpenClaw skill 格式兼容
- 已知限制：主动发送依赖 `context_token` 且**重启即丢**、无历史消息拉取、
  消息 2000 字符上限、token 会过期（详见 `docs/04` §4）

代价：每条消息起一个完整 coding agent 会话，比直接调 LLM API 重。

## 6. 我们没有被覆盖到的部分

调研下来，**没有一个现成项目同时具备**：

- ❌ 微信对话记账 **且** 电脑网页**实时**更新（SSE 推送，而非生成静态 HTML）
- ❌ 每日定时**主动**推送晨报
- ❌ 基于规则信号的**花费建议**（而非让 LLM 自由发挥）
- ❌ 转账与收支严格分离 + 跨月同期对齐的统计口径

这四条正是 `docs/01`~`docs/03` 设计的核心，也是自建的理由。

## 7. 最终采用的方案

**自写轻量桥接 + LLM API**，理由：

| 考虑 | 结论 |
| --- | --- |
| 微信通道 | iLink 协议只是几次 HTTP 调用，**自己实现 300 行以内**，零 npm 依赖 |
| 每笔账开销 | LLM 平台方案要跑一次完整 agent 轮次；自写只需**一次结构化抽取**，低一个数量级 |
| 隐性成本 | agent 平台有 heartbeat、system prompt、工具集等隐性开销，自写完全没有 |
| 依赖风险 | 不依赖小项目（golembot 322★）也不依赖大平台（OpenClaw 概念多、要升 Node） |
| 可控性 | 协议、提示词、路由、阈值全在自己手里 |

各项目的复用方式：

1. **微信协议** → 复用 **golembot**（MIT）的 iLink 实现思路，自己重写（`docs/04` §2）
2. **记账内核** → 按我们自己的设计做（`docs/02` + `docs/03`），
   **对照 `ezbookkeeping` 校验口径**（已补入 `modify_balance`）
3. **解析规则与置信度** → 参考 **auto-bookkeeping** 的阈值（0.6）与关键词表，
   自行设计加权评分（`docs/07`）
4. **报告与建议** → 无先例，按我们的 signals 设计自己做
5. **继续跟踪** → `VoltAgent/awesome-openclaw-skills` + ClawHub 的 Finance 分类

**先做 M-1**：用最小脚本跑通「扫码登录 → 收消息 → 发消息」，再投入记账内核开发
（见 `docs/05` §2）。
